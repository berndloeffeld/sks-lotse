# Postman collections and integration tests

Detail for the two Postman collections in `postman/`. The rules a change must follow are summarized in `CLAUDE.md` → Postman & integration tests; this page holds the how-to and the reasoning.

## API-reference collection (generated)
`postman/sks-lotse.postman_collection.json` is generated from the FastAPI app's live OpenAPI schema — never edit it by hand, it will just get overwritten.

- Regenerate after any API change: `./scripts/generate_postman_collection.sh` (needs the backend venv set up and Node/npx available), then commit the result. The same run rewrites the frontend's API types, `frontend/src/sks/api/schema.gen.ts` ([ADR-0046](adr/0046-api-types-generated-from-openapi.md)).
- The generator makes up a random example for any `pattern` or `enum` in the schema (a `pattern=` field, a `Literal[...]`), so the collection would differ on every run. Check such constraints in an `AfterValidator` on a plain `str` instead (`DigitsCode`, `TotpCode`, `ExamVariantField` in `backend/app/schemas/auth.py`); `backend/tests/test_openapi_determinism.py` fails locally when one slips in.
- `.github/workflows/backend-ci.yml` (`postman-collection` job) regenerates it in CI and fails the build if the committed file is out of date — a required check, so a stale collection blocks the merge.
- Every request in the collection uses a `{{baseUrl}}` variable (collection variable, default `/`). `postman/local.postman_environment.json.example` and `postman/production.postman_environment.json.example` are static, hand-maintained templates. **Copy each to the same name without `.example`** (gitignored — real copies hold live secrets, e.g. a JWT for testing protected endpoints) and import *those*, then switch between them via Postman's environment dropdown.
- When importing in Postman: use a plain one-off **Import**, not the Git-sync "Local Mode". That mode wants to upgrade the file to Postman's v3 YAML format, which would conflict with the JSON the generator produces and the CI freshness check expects, and it writes whatever you enter in the app back to disk, which can put a real secret into a tracked file; that is why the environment templates are `.example` files and the real copies are gitignored.

## Integration tests (hand-written, external / non-pytest)
`postman/integration-tests.postman_collection.json` is a separate, hand-written Postman collection — not the OpenAPI-generated API reference above. It black-box tests a real, running local backend over HTTP, among others: one no-token auth guard per router (the per-route check is pytest's `test_auth_guards.py`), CORS, security headers, the full OTP login round-trip (request → verify → `/me` → `/logout`), the question catalog/topics/progress endpoints incl. exam-variant filtering, profile updates (`PATCH /auth/me`), the email-change and self-delete flows (purpose-bound codes, per-user cap), the admin GDPR tools (incl. the non-admin 403s), and both OTP rate limits actually tripping. Point of it: runnable without a Python environment, e.g. in CI or by hand.

- Run it with `./scripts/run_integration_tests.sh` (wraps `newman run ... -e postman/local.postman_environment.json`, via `npx`) against an already-running local server (`cd backend && uvicorn app.main:app --reload`). Server requirements: `ADMIN_EMAILS` must include the collection's `adminEmail` (default `integration-admin@example.com`); `CHART_EXERCISES=admins` (the learner checks the flag's 404, the admin walks through a Kartenaufgabe); if `ALLOWED_EMAILS` is set it must include all six `integration-*@example.com` test addresses (`testEmail`, `profileEmail`, `profileNewEmail`, `adminEmail`, `victimEmail`, `blockedEmail`); use a freshly started server (rate-limit counters, dev-peek codes) on a scratch DB with the catalog seeded, and leave `RESEND_API_KEY` empty so the test addresses never get mail. It creates and deletes throwaway users. CI runs it in `backend-ci.yml`'s `integration-tests` job (real uvicorn + Postgres, `alembic upgrade head` first) — a required status check on `main` like the other PR jobs (see `CLAUDE.md` → Branch Strategy).
- The OTP round-trip needs the real, one-time plaintext code — pytest gets this for free by monkeypatching the email service in-process; an external HTTP client can't. `GET /api/v1/auth/otp/_dev-peek` (`backend/app/api/v1/auth.py`) exists to bridge that gap: it returns the last code generated for an email, 404s outright unless `ENVIRONMENT` is `development` or `test` (an opt-in allowlist, so it fails closed), is never populated at all otherwise either, and is excluded from the OpenAPI schema so it never surfaces in the API reference collection above. See [docs/adr/0011](adr/0011-dev-only-otp-peek-endpoint-for-external-integration-tests.md).
- The admin folder also needs the second factor ([ADR-0047](adr/0047-totp-step-up-for-admin-area.md)). No peek endpoint is needed for that: the collection enrols the admin test account, keeps the secret `/admin/mfa/enrol` returns, and computes the current code itself (RFC 6238 with `CryptoJS.HmacSHA1` in the pre-request scripts of the two `/admin/mfa/verify` requests). The folder ends by deleting the admin account, so a re-run enrols afresh.
- Not covered: `RedirectSecondaryDomainsMiddleware` (the canonical-domain redirect) — it keys off the `Host` header, which Postman/Newman silently drop rather than send as given (a restricted header, same idea as a browser's `fetch()`). Verify that one manually: `curl -i -H 'Host: sks-lotse.com' {{baseUrl}}/health`.
- Run order matters within the collection (documented in its own description too): Auth Flow's token is reused by Questions and Logout, Logout must come after both since it deliberately invalidates that token, and Rate Limiting must run last since it deliberately exhausts the OTP-endpoint quota for the caller's IP for the next hour.
- **The token comes from a header opt-in.** `Verify OTP` and `Admin 2FA - verify` return `access_token` in the body only when the request sends `X-Token-In-Body: true`; otherwise it is `null` and the session is just the cookie (ADR-0012 addendum 2026-10-14). The requests whose token later requests reuse send the header; `Verify OTP (account user)` and `Admin 2FA - verify` deliberately don't, assert `null` and read the token from the `Set-Cookie` header. In the generated `sks-lotse.postman_collection.json` the header is listed on both endpoints with the value `false`: set it to `true` before copying the token into `{{accessToken}}`.
- **A purchase needs the AGB in force.** The checkout requests come after `Accept AGB` in the Payments folder, which follows the 409 check (ADR-0041 addendum 2026-10-14).
- **Cookies are off except where they're the point.** `Verify OTP` also sets the httpOnly session cookie (ADR-0012), `get_current_user` reads it before any `Authorization` header, and Newman keeps a cookie jar across requests — so every request that authenticates via Bearer, or deliberately sends no credentials (the `... is rejected` auth guards), sets `"protocolProfileBehavior": {"disableCookies": true}`. Without it, the jar silently authenticates them and the guards pass requests they should reject. Only the requests with "session cookie" in their name leave cookies on, to test the cookie path itself. Do the same for any new request.
- **Keep it up to date:** the rule (a changed endpoint updates its requests and `pm.test` assertions in the same PR) is in [`CLAUDE.md`](../CLAUDE.md#postman--integration-tests). `backend/tests/test_integration_collection.py` enforces it in the normal pytest run (a route without a request, a request to a missing route, a request without `pm.test`, a Bearer or `... rejected` request without `disableCookies`), and CI executes the collection against a real server. A route with `include_in_schema=False` isn't discovered there: add it to `_UNDOCUMENTED_ROUTES`. A change to the server requirements above is also made in the collection description and in the header of `scripts/run_integration_tests.sh`.
